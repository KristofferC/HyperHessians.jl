Performance forensics · HyperHessians.jl vs ForwardDiff.jl

Anatomy of a speedup

Against released ForwardDiff, HyperHessians computes dense Hessians 3.2–6.5× faster at identical settings. But most of the arithmetic half of that gap turned out to be a ForwardDiff performance bug — a missing @inline found by reading the generated code, fixed here with a two-line patch. This report benchmarks against the patched ForwardDiff: 2.2–3.7× remains, and every remaining factor is structural — Hessian symmetry, an FMA-friendly memory layout, and a zero-allocation driver.

FACTOR 1

Symmetry: evaluate only the upper-triangular block pairs

1.94× · pure algorithm, independent of number types

ForwardDiff computes H = J(∇f): an outer chunked Jacobian wrapped around an inner chunked gradient. At chunk 8 that is ⌈256/8⌉² = 1024 evaluations of f, each producing an 8×8 block of the full square matrix. The symmetry of the Hessian is never used.

HyperHessians runs one HyperDual{8,8} pass per block pair (i, j ≥ i) (hessian_chunk_core!, src/hessian.jl:332): k(k+1)/2 = 528 evaluations for k = 32, each filling an 8×8 block of the upper triangle, then mirrors with symmetrize!. 1024 / 528 = 1.94×. Both eval counts were verified with a counting closure.

ForwardDiff — every 8×8 block of the full square
1024 evals × 64 entries = 65,536 Hessian entries computed
HyperHessians — upper-triangular 8×8 block pairs
528 evals × 64 entries = 33,792 entries computed, lower triangle mirrored — 1.94× fewer evaluations

Both grids depict the same 256×256 Hessian split into 8×8 blocks; each square is one evaluation of f on a vector of dual numbers. Both approaches redundantly recompute the primal and first-order parts on every pass; neither has an edge there. HyperHessians additionally reuses the ϵ₁ seed across the whole inner j-loop, touching only 16 array entries per eval, where ForwardDiff re-seeds the entire 162 KB dual array once per outer chunk.

FACTOR 2

Cheaper arithmetic per Hessian entry

1.0× (ackley) to 1.7× (rosenbrock) after patching ForwardDiff · this is where the number types differ

With the chunk size pinned, the payload is fixed: HyperDual{8,8} (1+8+8+64 floats) against a nested Dual{Dual{Float64,8},8} ((1+8)² floats) — identical 81-float, 648-byte structs computing identical derivative terms. Any timing difference is pure code generation. Investigating it turned up a genuine ForwardDiff bug (§2a, patched before all headline measurements) and one structural difference that survives the fix (§2b). 2a — The big per-op gap was a ForwardDiff bug: a missing @inline

Every DiffRules-generated Dual method funnels its result through dual_definition_retval (ForwardDiff/src/dual.jl:213). It carries no @inline annotation, and for fat nested duals Julia 1.12's inliner declines it — confirmed on both the released v1.3.0 and current master (v1.4.1). The entire body of a stock nested-dual multiply becomes two out-of-line calls plus a 648-byte memcpy. This is the actual, complete native code — the only arithmetic instruction is one scalar fmul:

In whole functions this multiplies out: stock rosenbrock_1 on nested 8×8 duals carries 28 out-of-line call sites in its loop body; on HyperDual{8,8} it carries zero. The fix is two characters short of trivial:

The patch — ForwardDiff/src/dual.jl applied to master (090ddbb) before all headline measurements 
-function dual_definition_retval(::Val{T}, val::Real, deriv::Real, partial::Partials) where {T}
+@inline function dual_definition_retval(::Val{T}, val::Real, deriv::Real, partial::Partials) where {T}
     return Dual{T}(val, deriv * partial)
 end
-function dual_definition_retval(::Val{T}, val::Real, deriv1::Real, partial1::Partials, deriv2::Real, partial2::Partials) where {T}
+@inline function dual_definition_retval(::Val{T}, val::Real, deriv1::Real, partial1::Partials, deriv2::Real, partial2::Partials) where {T}
     return Dual{T}(val, _mul_partials(partial1, partial2, deriv1, deriv2))

With the patch, the nested-dual multiply inlines into 493 straight-line instructions with zero calls and zero memcpy — and ForwardDiff's Hessians get 1.4–1.7× faster across the board. This deserves an upstream PR. Everything else in this report compares against the patched ForwardDiff.

2b — What survives the fix: lane shape and FMA fusion

Even patched, a nested-dual multiply compiles to 493 instructions with zero FMA, against 276 instructions with 104 packed fmla.2d for HyperDual — a 1.8× instruction-count ratio that matches the remaining 1.74× on multiply-dominated rosenbrock. Two causes. First, ForwardDiff's partials arithmetic is written as separate multiplies and adds, while every HyperDual accumulation goes through explicit muladd, which LLVM turns into fused multiply-adds. Second, the lane shape: both structs below are the same 648 bytes, but a nested Dual{T, Dual{T, V, 8}, 8} slices them into nine 9-float lanes — odd, straddling vector registers and cache lines at a different offset each time — where HyperDual{8,8} groups everything in 8-wide tuples: each lane exactly 64 bytes, one cache line, whole SIMD registers, and the ϵ₁₂ update a clean 8×8 outer-product-accumulate.

HyperDual{8,8} — 648 B, every lane is 8 doubles = whole vector registers
value ϵ₁ (8) ϵ₂ (8) ϵ₁₂ rows (8×8)
nested Dual 8×8 — same 648 B, but nine 9-double lanes with a ragged tail in every one
inner value 8 inner partials vector-width straggler

Each cell is one Float64; each bracket-group is one derivative lane the compiler must process as a unit. 8 doubles fill 2×AVX2 or 4×NEON registers exactly. 9 doubles are 4 full vectors plus a scalar straggler — every single lane, every single op.

2c — Scalar (f, f′, f″) rules: mostly a wash once FD inlines

HyperHessians evaluates each derivative rule as scalar expressions — sqrt: f′ = 1/2/f, f′′ = -2f′³ — and applies one fused chain rule, where ForwardDiff runs its first-order rule recursively in inner-dual arithmetic. Before the patch this looked like a 2.5× win on sqrt; after it, LLVM optimizes the recursive form nearly as well (14.7 vs 13.8 ns, and exp even favors ForwardDiff). What remains from the rule engineering is modest: the dedicated two-dual division rule and muladd-based chain rule keep / at 25.8 vs 22.7 ns, plus NaN-free monomial rules for integer powers as a correctness (not speed) difference.

ForwardDiff.hessian!(H, f, x, cfg) closes over gradient(f, y, …), which returns a fresh vector — one 18.4 KB Vector{Dual} allocation per outer chunk, 32 times per Hessian, plus GC pressure. Extraction is two-stage: the inner gradient extracts into that dual-typed vector, then the Jacobian layer copies partials out into H. HyperHessians fills its config buffer once and writes each 8×8 ϵ₁₂ block straight into H.

RULED OUT

What does not explain the gap

each hypothesis checked and rejected

CHECKED

Chunk size. Everything in this report pins both packages to chunk 8, so chunk choice is out of the equation by construction. It also isn't hiding anything: letting ForwardDiff use its own default heuristic changes its ackley total by under 10%. HH's own sweep puts 8 at the optimum for HyperDuals because HyperDual{16,16} (2.3 KB) spills registers — hence maxchunksize = 8.

CHECKED

Algebraic redundancy in nested duals. None for */+: expanding the nested product gives outer partial i = v₂A₁[i,:] + a₁[i]b₂ + v₁A₂[i,:] + a₂[i]b₁ — exactly the HyperDual ϵ₁₂ row, same flop count. The redundancy that does exist is 2c: rule evaluation in dual arithmetic.

CHECKED

Extra transcendental calls. Identical counts in both (one exp, one sincos per element in ackley). The win is in everything around them.

CHECKED

Tag checking. Compile-time only; no runtime cost.

CHECKED

@fastmath rule specialization. Present in HyperHessians but unused by these benchmarks — the DiffTests functions don't use @fastmath, so it contributes nothing to the committed numbers.

Sanity check on this machine (chunk 8 both, patched FD): evals × per-eval cost predicts the totals — FD 1024 × 16.4 µs = 16.8 of 20.4 ms; HH 528 × 16.0 µs = 8.5 of 9.1 ms. The residuals are factor 3, and the three factors multiply to 2.2 (ackley) and 3.7 (rosenbrock) against measured 2.23× and 3.67×.

The largest single finding is ForwardDiff's, not HyperHessians'. The missing @inline on dual_definition_retval costs stock ForwardDiff 1.4–1.7× on every nested-dual Hessian (confirmed on v1.3.0 and master v1.4.1). Users today experience the stock rows in the table above; the patch should go upstream, at which point the honest gap is the patched rows.

Machine dependence. The committed arrowlake-s numbers were taken with stock ForwardDiff and package-default chunks; the x86/AVX2 codegen gap should also narrow with the patch, but re-running that machine's sweep is the way to know.

HVP wins for a structural reason. HyperDual{N1,N2} supports asymmetric lanes, so hvp seeds ϵ₂ with the tangent directly (HyperDual{8,1}) and chunks only ϵ₁ — 1.8–3.6× over DI/ForwardDiff's pushforward-of-chunked-gradient nesting (measured against stock ForwardDiff).

Methodology. All measurements: Julia 1.12.6, HyperHessians at e5b8b4c, ForwardDiff master (090ddbb, v1.4.1) with the two-line @inline patch applied and Pkg.developed into the benchmark environment ("stock" rows: unpatched). BenchmarkTools minimum times, single thread, DiffTests inputs with fixed seed, chunk size pinned to 8 for both packages (ForwardDiff.Chunk{8}() / HyperHessians default) so both use the same 81-float dual payload. Evaluation counts via counting closure; codegen via code_native/code_llvm (assembly shown is ARM64/NEON, lightly trimmed of debug directives, symbol suffixes shortened). Experiment scripts and the patch: benchmark/why-faster/ in the repository. Committed reference numbers from benchmark/results/summary.md (arrowlake-s, 24 threads, serial configs, package-default chunks, stock ForwardDiff).
