Factor 1 · 1.94×

A Hessian is symmetric. Compute half of it.

ForwardDiff — every 8×8 block of the full square
32² = 1024 evaluations of f
HyperHessians — upper-triangular block pairs, then mirror
32·33/2 = 528 evaluations of f  →  1.94× fewer
  • Jacobian-of-gradient has no place to exploit symmetry: each outer chunk needs the full gradient.
  • Independent ϵ₁ / ϵ₂ seeds address blocks (i, j) directly — evaluate only j ≥ i.
  • Eval counts verified with a counting closure; block pairs are embarrassingly parallel (7.1× on 8 cores).
same 256×256 Hessian, same 8×8 blocks, in both grids

Factor 2 · mechanism A

Lane shape: 8 is a SIMD width. 9 is not.

HyperDual{8,8} — every derivative lane is 8 doubles = whole registers (one zmm)
nested Dual 8×8 — same 648 bytes sliced into nine 9-double lanes, a straggler in every one

Each cell is one Float64; each group is a lane the compiler processes as a unit. 8 doubles = 4×NEON, 2×AVX2, or exactly 1×AVX-512 register. 9 doubles = a full vector set plus a scalar straggler — on every lane, in every operation. HyperHessians also fuses every accumulation through muladd; the nested layout's mul-then-add never fuses.

on 2-wide NEON the straggler is cheap — on 8-wide AVX-512 it is not →

Factor 2 · mechanism B

Flat layouts let LLVM delete dead derivative lanes

DiffTests.rosenbrock_1the constants are duals
function rosenbrock_1(x)
    a = one(eltype(x))     # a dual! ϵ ≡ 0
    b = 100 * a            # a dual! ϵ ≡ 0
    result = zero(eltype(x))
    for i in 1:length(x)-1
        result += (a - x[i])^2 +
                  b * (x[i+1] - x[i]^2)^2
    end
    result
end
  • Every iteration multiplies by a dual whose 80 derivative floats are known zeros.
  • Through the flat, fully-inlined HyperDual code, LLVM constant-folds the dead lanes away — the op collapses to near real×dual cost.
  • Through the nested representation the folding largely fails: the zeros are computed.
  • Evidence: rewrite with literal 1 and 100 and the two types run at parity (33.6 vs 35.0 ns/element); with dual constants the gap is 1.74×.
same zeros, same algebra — transparency to the compiler differs

The Jacobian-of-gradient driver allocates a fresh dual-typed gradient vector on every outer chunk and re-seeds the whole input array; the hyper-dual driver fills one buffer per Hessian, seeds 16 entries per pass, reuses the ϵ₁ seed across the inner loop, and writes each 8×8 block straight into H.

Takeaways

Speed came from structure the compiler can see

  • Exploit the math: symmetry alone halves the work — 1.94× before any code tricks.
  • Shape data for the machine: 8-wide flat lanes are register-exact and FMA-fusable; nested 9-wide lanes cost shuffles, gathers, and stragglers on every op.
  • Stay transparent to LLVM: flat + fully inlined means dead derivative lanes fold away and intermediates never touch memory.
  • Keep the driver silent: zero allocations, 16 seed writes per pass, blocks written straight into H.
  • Decompose your benchmarks: a speedup you can't factor is a speedup you don't understand.
